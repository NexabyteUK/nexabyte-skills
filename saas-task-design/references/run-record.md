# Run record

Keep this record short enough to review alongside the proposed screen. Record facts and decisions, not a transcript of the agent's reasoning.

## Inputs

- Story and target screen or flow.
- Repository and exact source revision; original capture.
- Current user decisions and behaviour sources, with dates or saved snapshots.
- Voice and design references; their versions or hashes where available.
- Scope, permitted changes and local/remote boundary.

## Customer task

Who arrives, why, what they need to understand, the available decision, and what the system handles without them.

## Evidence

| Claim or action | Observed / specified / unknown / proposed | Source | Design consequence |
| --------------- | ----------------------------------------- | ------ | ------------------ |

## Content decisions

| Existing content | Visible / on demand / removed | Reason for this customer's task |
| ---------------- | ----------------------------- | ------------------------------- |

Explain any changed terminology or new interaction. Name an unsupported automatic alternative as a product question, not as shipped behaviour.

## Reproduction and checks

Record the base revision, patch, build/capture commands and required tools. Include scope of tests, rendered sizes/themes, keyboard/interaction results, independent comprehension answers and unresolved concerns. Preserve the first proposal if later revisions are compared against it.

## Next decision

State what the user is reviewing and which behavioural questions need their decision. Do not translate a successful build into product approval.
